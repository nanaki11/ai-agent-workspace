# 課題・リスク・変更の管理

## 実行契約
作業前に [実行・品質規約](references/consulting-delivery-standard.md) を読む。単独利用時も同じ規約を適用し、作業モードに応じて記録と検証を絞る。


課題＝すでに起きている問題。リスク＝まだ起きていないが、起きると影響がある不確実なこと。

## 1. 課題管理
### 課題管理表の列
| 列 | 内容 |
|---|---|
| ID／起票日／起票者 | |
| 件名・内容 | 何が起きていて、何に影響しているか |
| 影響 | スケジュール／コスト／品質／スコープ |
| 優先度 | 高（マイルストーンや本番に影響）／中／低 |
| 担当者／期限 | 担当は個人名で1人 |
| ステータス | 未着手／対応中／確認待ち／完了 |
| 対応内容・経過 | 日付つきで追記していく |
| エスカレーション先 | 必要な場合 |

### 課題表を分析するとき
- 期限切れの課題と、2週間以上動いていない課題を抜き出す
- 担当者ごと・チームごとの件数の偏り
- 新しく起きた件数と、完了した件数の推移（溜まっているかどうか）
- 似た課題が何度も起きていないか → 根本原因（要件の曖昧さ、体制、プロセスなど）を指摘する
- エスカレーションの基準：優先度「高」で期限を過ぎた／チームの中で決められない／複数チームにまたがる

## 2. リスク管理
### 洗い出しの観点（ITプロジェクトでよくあるリスク）
- 要件：要件が固まらない、利用部門の関与が足りない、スコープが膨らむ
- 体制：キーマンへの依存、スキル不足、ベンダーの体制変更
- 技術：新しい技術・製品の初めての採用、性能、他システムとの連携
- データ移行：データの品質、件数、移行時間
- スケジュール：他プロジェクトとの依存、繁忙期とのぶつかり
- 外部：法改正、製品のサポート終了、価格改定

### リスク登録簿
| ID | リスク（〜により、〜が起き、〜になる） | 発生確率 1-5 | 影響度 1-5 | スコア | 対応戦略 | 対策 | 担当 | 予兆（トリガー） | 状態 |
|---|---|---|---|---|---|---|---|---|---|

- スコア＝発生確率×影響度。15以上＝高、8〜14＝中、7以下＝低
- 対応戦略：回避（原因をなくす）／転嫁（契約・保険）／軽減（確率や影響を下げる）／受容（起きたときの対応だけ決めておく）
- 予兆：リスクが起きかけていると分かるサイン（例：「要件の確定が2週間遅れたら」）
- 高リスクは毎週見直す。起きてしまったら課題に移す

## 3. 変更管理
変更要求が来たら、承認する前に影響を分析する。
| 項目 | 内容 |
|---|---|
| 変更内容と理由 | |
| 影響：スコープ | 増える／減る機能 |
| 影響：スケジュール | マイルストーンへの影響（日数） |
| 影響：コスト | 追加の工数・費用 |
| 影響：品質・リスク | 再テストの範囲、新しく生まれるリスク |
| 選択肢 | 今回やる／次のリリースに回す／やらない |
| 推奨と判断者 | 誰が決めるか（金額や影響の大きさで決める人を変える） |

- 小さな変更でも、たまると大きくなる。変更の件数と累計の影響を報告する

## 出力
- 課題・リスク管理表（xlsx）
- 分析結果：要注意の課題・リスク上位5件、傾向、根本原因、打ち手
- 変更要求の影響分析と推奨

## 実務での追加検証
- 確率・影響の1〜5は順序尺度であり実際の期待損失額ではない。低頻度でも致命的なリスクを積スコアだけで低優先にしない。
- 対策後の残余リスク、発動条件、担当・期限を記録する。発生したリスクは元IDを保って課題と関連づける。
- 変更要求は要件・費用・効果・納期・品質・決議事項への累積影響を評価し、未承認の変更を計画へ混入させない。
