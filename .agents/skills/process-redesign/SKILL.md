# 業務改革（To-Be設計）

## 手順
1. **課題を集めて分類する**（bpm-process-mapping の課題一覧から）
   - 分類：プロセス／ルール／組織・人／システム／データ
   - 課題は「誰が・何に・どう困っているか」で書く（「非効率」だけで終わらせない）
2. **真因を特定する**
   - Why ツリー（なぜを3〜5回）で、症状と原因を分ける
   - 複数の課題に共通する原因を探す（例：マスタが部門ごとにばらばら）
3. **数字で大きさを測る**（quantitative-analysis）
   - 業務量 ＝ 件数 × 1件あたりの時間。大きい業務から手を付ける
   - ボトルネック（待ち時間、手戻り率、滞留件数）を数える
4. **改善の方向を出す**

   | 観点 | 問い |
   |---|---|
   | E 排除 | その作業はなくせないか |
   | C 結合 | 他の作業とまとめられないか |
   | R 交換 | 順番や担当を変えられないか |
   | S 簡素化 | もっと簡単にできないか |
   | 標準化 | 部署ごとのやり方を1つにできないか |
   | デジタル化 | システム化、RPA、AI、セルフサービス、ペーパーレスにできないか |
   | 集約 | シェアードサービスやアウトソースにできないか |

5. **To-Be を設計する**
   - 設計方針を先に決める（例：「入力は発生源で1回だけ」「承認は2段階まで」「例外は全体の1割以下にする」）
   - To-Be 業務フローを、As-Is と同じ記法で作る（drawio-diagram）
   - As-Is との差分一覧：なくなる作業／変わる作業／新しい作業、担当の変化、業務量の変化
6. **Fit&Gap（パッケージ・SaaSを入れる場合）**

   | 業務要件 | パッケージ標準の機能 | 判定 | 対応方針 | 工数・費用 |
   |---|---|---|---|---|

   - 判定：Fit（標準で対応）／Gap
   - Gap の対応方針は優先順で：①業務を標準に合わせる → ②設定で対応 → ③運用で回避 → ④アドオン開発（最後の手段。理由を書く）
7. **施策を選んで並べる**
   - 効果（業務量の削減、品質、リスク）×実現の難しさ（費用、期間、組織の抵抗）の2×2
   - すぐやる（Quick Win）／計画的にやる／見送る、に分ける
8. **定着させる（チェンジマネジメント）**
   - 役割ごとの影響度（何が変わるか、どれくらい大きいか）
   - 教育計画（対象、内容、時期）、マニュアル、問い合わせ窓口
   - 定着を測る KPI（kpi-design）と、確認の時期（導入後1か月・3か月）

## 出力フォーマット
```
## 結論（To-Be の要点と効果）
## 課題の構造（真因）
## To-Be 設計方針
## To-Be 業務フロー（.drawio）と As-Is との差分
## Fit&Gap（該当する場合）
## 施策一覧と優先順位
| # | 施策 | 解決する課題 | 効果 | 難易度 | 区分 | 時期 |
## 定着化計画
```
