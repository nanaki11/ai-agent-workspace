# 技術・製品・ベンダーの選定

## 実行契約
作業前に [実行・品質規約](references/consulting-delivery-standard.md) を読む。単独利用時も同じ規約を適用し、作業モードに応じて記録と検証を絞る。


## 原則
- 特定のベンダーや製品に肩入れしない。評価基準は候補を見る前に決める
- 製品の機能・価格・サポート期限は変わる。記憶で書かず desk-research で最新の情報を確認し、確認日を書く
- 選んだ理由と、選ばなかった理由の両方を残す

## 手順
1. **要件を確認する**：requirements-definition の Must 要件と非機能要件、ea-design のアーキテクチャ原則
2. **候補を絞る**
   - ロングリスト（5〜10個）→ 必須条件で足切り → ショートリスト（2〜4個）
   - 必須条件の例：必須機能がある／求める稼働率を満たす／データを国内に置ける／サポート期限が十分ある
3. **RFI**（情報提供依頼）：会社概要、製品概要、導入実績、概算費用、ロードマップを集める
4. **RFP**（提案依頼書）を作る
5. **評価する**（quantitative-analysis の評価マトリクス）

   | 評価軸 | 重みの例 | 見るところ |
   |---|---|---|
   | 機能の適合 | 30% | Fit&Gap の Fit の割合、Gap を埋める方法 |
   | 非機能 | 15% | 性能、可用性、セキュリティ、拡張性 |
   | コスト（TCO 5年） | 20% | 初期費用、ライセンス、保守、運用、アドオン |
   | ベンダーの力 | 15% | 実績、体制、財務の安定性、サポート |
   | 将来性 | 10% | 製品のロードマップ、市場での地位、技術の新しさ |
   | 導入・移行のしやすさ | 10% | 期間、移行ツール、教育 |

   - 点数の基準（1／3／5点）を先に決める
   - 評価は複数人で行い、点の差が大きい項目は話し合って決める
6. **PoC**（必要な場合）：検証項目、合格基準、期間、環境、費用
7. **決めて記録する**：推奨案、次点の案、条件（交渉で詰めること）、ADR

## RFPの目次
```
1. 背景と目的
2. 対象範囲（業務・システム）
3. 要件（機能要件、非機能要件。Must／Want を区別）
4. 現行システムの概要
5. 体制・スケジュールの想定
6. 提案してほしい内容（構成、体制、スケジュール、見積の内訳）
7. 評価方法と選定スケジュール
8. 提案のルール（形式、期限、問い合わせ窓口、機密保持）
```

## ADR（アーキテクチャ決定記録）
```
# ADR-<番号>: <決めたこと>
- ステータス：提案中／承認済み／廃止（<後継のADR>）
- 日付・決めた人：
## 背景
何を決める必要があったか。制約や前提。
## 決定
何を選んだか。
## 検討した選択肢
| 選択肢 | 良い点 | 悪い点 |
## 結果
この決定で良くなること、受け入れるトレードオフ、今後見直すべき条件。
```

## 出力
- 評価結果の比較表と推奨案（理由つき）
- TCO 比較（5年）
- RFP（docx）
- ADR（md）

## 実務での追加検証
- Mustは適合／不適合／未確認で判定する。未確認を適合・ゼロ点に丸めず、確認担当・期限・選定への影響を残す。
- 採点に根拠E・確認日・製品エディション・地域を付ける。ベンダーの申告とPoC確認を分ける。
- TCOの期間と含有費用をそろえ、移行・並行稼働・教育・解約費を含める。重みと前提を動かし、順位が逆転する条件を示す。
- PoCには要件R、測定条件、合否基準、証跡を紐づける。ADRに次点案、採用条件、未解決事項、見直し条件を記録する。
