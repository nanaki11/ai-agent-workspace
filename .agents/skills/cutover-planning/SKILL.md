# 移行・切り替え計画

## 1. 移行方式
| 方式 | 内容 | 向いている場面 | リスク |
|---|---|---|---|
| 一括 | 全部を一度に切り替える | 規模が小さい、並行稼働ができない | 失敗したときの影響が大きい |
| 段階 | 拠点・機能・部門ごとに順番に | 規模が大きい、拠点が多い | 期間が長い、新旧をつなぐ仕組みが要る |
| 並行 | 新旧を同時に動かし結果を比べる | 正確さが最優先（会計・給与など） | 利用部門の負担が二重になる |

## 2. データ移行
| 項目 | 内容 |
|---|---|
| 対象 | データの種類、件数、期間（何年分を移すか） |
| 移行元・移行先の対応 | 項目の対応表、コードの変換表 |
| クレンジング | 重複、欠損、表記ゆれ、使われていないデータ。誰がいつ直すか |
| 方法 | ツール、手作業、移行用のプログラム |
| 検証 | 件数の一致、金額の合計の一致、サンプルの目視、業務での確認 |
| リハーサル | 最低2回（1回目：手順の確認、2回目：本番と同じ時間で通す）。時間を計る |

## 3. 切り替えのタイムチャート
| No | 開始 | 終了 | 作業 | 担当 | 確認者 | 判定ポイント | 切り戻し手順 |
|---|---|---|---|---|---|---|---|

- 分単位で書く。作業ごとに担当と確認者を決める
- 判定ポイント（ここで問題があれば止める）と、切り戻しできる最後の時刻（ポイント・オブ・ノーリターン）をはっきり書く
- 連絡体制：連絡先の一覧、報告のタイミング、エスカレーションの経路

## 4. Go/No-Go 判定
| 判定項目 | 基準 | 結果 | 判定 |
|---|---|---|---|
| テスト | 総合テスト・受け入れテストが終了、重大バグが0 | | |
| データ移行 | リハーサルで件数・金額が一致、時間内に終わった | | |
| 性能 | 非機能要件を満たした | | |
| 運用 | 運用手順・監視・バックアップが準備できた | | |
| 業務 | 利用者の教育が完了、マニュアルがある | | |
| 体制 | 切り替え当日と本番後のサポート体制が決まっている | | |
| 切り戻し | 切り戻しの手順をリハーサルで確認した | | |
| 未解決の課題 | 本番に影響する課題が0、または回避策がある | | |

- 判定会議の日時、出席者、決める人を決めておく
- 条件付きGo（○○を前提に進める）の場合は、条件と期限を記録する

## 5. 業務の移行
- 利用者ごとの教育（対象、内容、時期、方法）
- マニュアル、FAQ
- 問い合わせ窓口と、本番後の集中サポート（期間、体制、問い合わせ件数の見込み）
- 旧システムの扱い（参照用に残す期間、停止日、データの保管）

## 6. 本番後（ハイパーケア）
- 期間（通常2〜4週間）、毎日の確認会、問い合わせ・障害の件数の推移
- 終了の基準：重大な障害が○日間なし、問い合わせ件数が一定以下

## 出力
- 移行計画書（方式、範囲、体制、スケジュール、リスク）
- データ移行計画、切り替えタイムチャート（xlsx）
- Go/No-Go 判定シート
