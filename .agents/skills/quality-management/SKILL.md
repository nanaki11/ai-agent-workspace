# 品質管理

## 実行契約
作業前に [実行・品質規約](references/consulting-delivery-standard.md) を読む。単独利用時も同じ規約を適用し、作業モードに応じて記録と検証を絞る。


## 1. 品質計画
- 品質の目標（何をもって品質が良いとするか）
- 工程ごとの品質活動（レビュー、テスト）と、誰が行うか
- 品質指標と基準値（下の3を見る）
- 基準を外れたときの対応（分析、再レビュー、追加テスト）

## 2. テストレベル
| レベル | 目的 | 開始の基準 | 終了の基準 |
|---|---|---|---|
| 単体テスト（UT） | プログラム単位の正しさ | コードレビューが完了している | 計画したケースを100％実施、未解決の重大バグが0 |
| 結合テスト（IT） | 機能どうし・システムどうしの連携 | UT が終了している | ケースを100％実施、バグが収束している |
| 総合テスト（ST） | 業務の流れと非機能（性能・障害時の動き） | IT が終了し、環境が本番と同じ構成 | 業務シナリオがすべて通る、非機能要件を満たす |
| 受け入れテスト（UAT） | 利用部門が業務で使えることを確認する | ST が終了し、マニュアルがある | 利用部門が合格と判断した |

- テストケースは要件にさかのぼれるようにする（requirements-definition のトレーサビリティ）

## 3. 品質指標
| 指標 | 計算 |
|---|---|
| レビュー指摘密度 | 指摘件数 ÷ 文書のページ数（または規模） |
| テスト密度 | テストケース数 ÷ 規模（KLOC または FP） |
| バグ密度 | バグ件数 ÷ 規模 |
| バグの収束 | 累積バグ件数の推移（信頼度成長曲線）が横ばいになっているか |
| 未解決バグ | 重要度ごとの未解決の件数と、平均の解決日数 |

- 基準値は組織の過去の実績を使う。実績がなければ業界の公開データを参考にし、出典を書く
- 指標が基準より**良すぎる**場合も疑う（レビューやテストが甘い可能性がある）

## 4. バグの分析
- 分類の軸：重要度、作り込んだ工程（要件・設計・実装）、見つけるべきだった工程、種類（ロジック、データ、IF、画面など）、機能・モジュール
- 偏りを見る：特定の機能やチームにバグが集中していないか → 集中しているところは再レビュー・追加テストをする
- 見逃し：本来もっと前の工程で見つけるべきだったバグの割合 → 前の工程の品質活動を見直す

## 5. 品質報告
```
## 品質の総合評価：🟢／🟡／🔴
## 指標と基準値の比較
| 指標 | 実績 | 基準値 | 評価 |
## バグの収束状況（累積件数の推移）
## 偏り・見逃しの分析
## 対策と、終了判定の見込み
```

## 実務での追加検証
- 件数・密度は規模、テスト実施率、対象機能、重要度と合わせて評価する。検出件数の減少だけで収束としない。
- 必須要件の未検証・重大欠陥・データ不足を識別し、終了判定の根拠を保存する。例外は承認者と残余リスクを記録する。
- 是正後に再テストと同類不具合の横断点検を行い、再発防止の責任者・期限・確認方法を定める。
