# 要件定義

## 手順
1. **業務要件**：To-Be 業務フロー（process-redesign）から、システムに求めることを洗い出す。業務フローの作業ごとに「システムで何をするか」を書く
2. **機能要件**
   - 機能一覧

     | 機能ID | 機能名 | 概要 | 対応する業務（フローID） | 利用者 | 優先度 |
     |---|---|---|---|---|---|

   - 優先度は MoSCoW（Must／Should／Could／Won't）
   - 主要な機能は、ユースケースかユーザーストーリーで書く
     - 「〈利用者〉として、〈目的〉のために、〈機能〉がほしい」
     - 受け入れ基準：「〈前提〉のとき、〈操作〉すると、〈結果〉になる」
   - 一覧：画面一覧、帳票一覧、インターフェース一覧（ea-design と共通）、バッチ一覧
3. **非機能要件**（IPA 非機能要求グレードの6大項目）

   | 大項目 | 決めること | 書き方の例 |
   |---|---|---|
   | 可用性 | 稼働時間、稼働率、RTO／RPO、災害対策 | 平日 8〜22 時、稼働率 99.9%、RTO 4時間、RPO 1時間 |
   | 性能・拡張性 | 応答時間、処理件数、同時利用者数、データ量の伸び | オンラインの画面応答 3 秒以内（90 パーセンタイル）、同時 500 ユーザー |
   | 運用・保守性 | 運用時間、監視、バックアップ、保守の体制 | 日次でフルバックアップ、7世代保管 |
   | 移行性 | 移行方式、移行するデータの量、移行に使える時間 | 停止時間は土日の 48 時間以内 |
   | セキュリティ | 認証、権限、暗号化、ログ、脆弱性対策、準拠する規程 | 多要素認証、操作ログ 1 年保管 |
   | システム環境 | 基盤、利用端末・ブラウザ、制約 | 最新版の Edge／Chrome |

   - 数値で書く。決められない項目は「未決」とし、決める人と期限を書く
4. **データ要件**：主要なエンティティ、件数、保管期間、マスタの正（ea-design）
5. **制約・前提**：予算、期限、使う製品、法令、他プロジェクトとの関係
6. **トレーサビリティ**：業務要件 → 機能要件 → テスト（quality-management）を ID でつなぐ

## 要件の書き方
- 1つの要件は1つの文で書く
- 曖昧な言葉を使わない：「高速に」「適切に」「柔軟に」「など」「できるだけ」→ 数値か条件に置き換える
- テストで確かめられる書き方にする（受け入れ基準がある）
- 「〜できること」と主語を明確にする（誰が・何を）

## 要件定義書の目次
```
1. 概要（目的、スコープ、前提・制約）
2. 業務要件（To-Be 業務フロー、業務ルール）
3. 機能要件（機能一覧、ユースケース、画面・帳票・IF・バッチ一覧）
4. 非機能要件（6大項目）
5. データ要件
6. 移行要件
7. 未決事項（内容、決める人、期限）
付録：用語集、トレーサビリティ表
```

## チェック
- [ ] すべての To-Be の業務の作業が、機能か運用のどちらかでカバーされている
- [ ] Must の機能に受け入れ基準がある
- [ ] 非機能要件がすべて数値か、未決として管理されている
- [ ] 曖昧な言葉が残っていない
